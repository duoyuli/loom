这是一篇围绕 ReAct 风格 Agent 重试机制的结构性诊断。它最有长期价值的判断不是某个 90.8% 的数字，而是指出：只要工具名仍由模型在运行时自由输出、错误又不分类型地共享一个全局重试计数器，系统就会把预算消耗在永远不会成功的错误上。

## 这份资料是什么

- 资料来自 Towards Data Science 文章摘录，作者通过确定性模拟分析 ReAct 类工具调用循环的失败模式。
- 文中包含可复现代码和较明确的限制说明，因此适合当作架构反例与可靠性设计样本。
- 百分比结果来自作者模拟，不应直接外推为所有生产环境都会出现同样比例。

## 主要观点

1. 让模型在运行时输出工具名称字符串，是 ReAct 代理里一个被低估的结构性风险。
2. `TOOL_NOT_FOUND` 这类错误不是“也许下次会好”的瞬时故障，而是不可重试错误；若和网络抖动共用重试预算，就会挤占真正可恢复故障的空间。
3. 错误分类、单工具熔断器和确定性工具路由，比继续微调 prompt 更能解决这类可靠性问题。
4. 监控若只看成功率、延迟和总重试次数，很可能看不到系统正在被不可重试错误悄悄拖垮。

## 关键内容

### 问题根源：字符串级工具路由

- 文中把 `TOOLS.get(tool_name)` 视为问题核心。
- 一旦模型幻觉出不存在的工具名，返回值就是 `None`；如果系统仍把它当作“重试看看”的候选，就会稳定浪费预算。

### 三个结构性修复

- **错误分类**：先判断错误能否通过重试改变，再决定是否消耗预算。
- **单工具熔断器**：不要让所有失败共享一个全局重试计数器。
- **确定性工具路由**：让模型输出步骤类型，再由代码层的映射字典解析成具体工具，从结构上消掉“幻觉工具名”。

### 证据边界

- 文中 90.8% 废重试来自作者设定参数下的确定性模拟。
- 真正值得长期保留的不是这个数字，而是“不可重试错误不能和可重试错误共用治理逻辑”这一架构性质。
