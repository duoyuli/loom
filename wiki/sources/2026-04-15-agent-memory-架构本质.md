这是一篇从系统设计角度继续压实 Agent Memory 的综述。它对本知识库最有长期价值的判断不是再重复“记忆很重要”，而是把 Memory 的难点重新压回治理：边界怎么划、对象怎么建模、记忆单元该包含哪些维度、写入/管理/读取三条链路如何协同。

## 这份资料是什么

- 资料来自一篇微信公众号长文摘录，作者延续此前关于 Harness 和 Memory 的思考，试图给 Agent Memory 一套更明确的工程框架。
- 文章带有较强作者判断色彩，但结构化程度高，适合作为概念页的补强材料。
- 它与已有的 [浅谈 Agent Memory](2026-04-12-浅谈-agent-memory.md) 主题接近，但更强调边界、建模对象和治理链路。

## 主要观点

1. 长上下文解决的是带宽而不是建模，真正难的是让昨天学到的东西以可更新、可追责的方式进入今天。
2. Memory 不能与 `State / Policy / Profile` 混用；它保存的是可跨时延续并影响未来决策的结构化历史。
3. 记忆应同时建模用户、任务、世界和自我四类对象，而不是只盯着用户偏好。
4. 单条记忆至少应包含内容、类型、置信度、来源、作用域、时间与衰减等维度，否则只是无法治理的文本碎片。
5. 记忆系统是一条 `write -> manage -> read` 闭环；其中管理链路往往最容易被忽略，但决定系统是资产还是垃圾堆。
6. 记忆的高级形态不是“留下结论”，而是保留可修正、可遗忘、可持续更新的模型。

## 关键内容

### 先划边界

- 文中把 `State` 定义为 session 内短期运行态，把 `Policy` 定义为权限和安全边界，把 `Profile` 定义为用户模型的低维快照。
- 这一划分很重要，因为它阻止“任何能跨会话保存的东西都叫记忆”这种概念膨胀。
- 作者也明确反对把“蒸馏 = 记忆”混为一谈，认为摘要只是管理链路中的一步。

### 四个建模对象与六维记忆单元

- 四类对象分别是：用户模型、任务模型、世界模型、自我模型。
- 六个最值得保留的维度是：内容、类型、置信度、来源、作用域、时间与衰减。
- 这一套建模方式的价值在于，它把“记忆是字符串”推进成“记忆是可查询、可冲突处理、可更新的状态对象”。

### 三条链路：写入、管理、读取

- 写入的核心不是“值不值得存”，而是预算约束下的边际价值判断。
- 管理链路负责整合、冲突处理、衰减、来源追踪和权限治理，是系统长期是否失控的分水岭。
- 读取不应停留在语义相似召回，而应转向“任务约束驱动的检索-推断耦合”。
