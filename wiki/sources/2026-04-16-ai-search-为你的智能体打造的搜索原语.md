这是一篇围绕 Cloudflare AI Search 的产品与架构说明。它对本知识库最有长期价值的部分，不是某个云服务上新，而是把“搜索”明确写成 Agent 的基础原语：检索不只是向量库，而是作用域管理、混合召回、索引维护和跨实例组合查询组成的运行时底座。

## 这份资料是什么

- 资料来自 Cloudflare AI Search 的发布说明，经 bestblogs 摘录。
- 文章以客服 Agent 为例，说明如何同时检索共享产品文档和单客户历史记录。
- 内容兼有产品介绍和架构示例，适合用来理解“Agent 检索基础设施应承担什么职责”，不适合直接当作跨平台通用结论。

## 主要观点

1. 对 Agent 而言，搜索不应被理解为单个向量索引，而应是一组可直接接入运行时的检索原语。
2. 搜索作用域本身应可编程：按客户、按 Agent、按语言创建独立实例，比把所有数据混进一个总索引更贴近真实多租户场景。
3. 混合搜索应同时保留语义匹配和关键词精确性，再用融合排序处理结果，而不是预设某一种检索总是足够。
4. 跨实例查询说明检索对象经常天然分层：共享知识和局部历史应可并查，但不一定应该先物理合并。
5. 文中把“memory”也归为搜索问题的一部分；这对检索基础设施有解释力，但不足以覆盖写入、衰减、冲突处理和遗忘等完整记忆治理问题。

## 关键内容

### 搜索作为 Agent 基础设施

- 文章把代码仓库、支持工单、客户历史、共享产品文档放在同一类问题里：都要求在正确时间把正确信息送回模型。
- 与其分别搭建向量库、关键词检索和索引同步流程，作者主张把这些能力收束为可直接调用的托管搜索原语。

### 作用域：实例与命名空间

- 新的 `ai_search_namespaces` 绑定允许在 Worker 运行时动态创建、删除和管理搜索实例。
- 这意味着“一个 Agent 的知识边界”不必在部署时写死，而可以随用户、任务或租户动态生成。
- 文章示例里，`product-knowledge` 承担共享知识库，`customer-<id>` 承担单客户历史；两者保持隔离，但可在同一次查询里共同参与排序。

### 检索结构：混合搜索与跨实例查询

- 文中默认采用 `vector + BM25` 并行检索，再做融合排序。
- 它还强调元数据提升和跨实例统一排序，说明检索质量并不只取决于 embedding，还依赖时间、来源和作用域这些附加结构。
