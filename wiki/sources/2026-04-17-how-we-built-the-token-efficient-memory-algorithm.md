这是一篇由 Mem0 发布的记忆算法说明。它最有长期价值的判断不是某组 benchmark 分数，而是把 Agent 外部记忆重新定义为一个受 token 预算约束的系统问题：写入、检索和推理必须一起设计，不能把“多塞一点上下文”误当成记忆能力本身。

## 这份资料是什么

- 资料来自 `x.com` 上的产品与研究说明帖，用于发布 Mem0 在 2026 年 4 月上线的新记忆算法。
- 正文一边解释旧版与新版算法差异，一边给出在 `LoCoMo`、`LongMemEval` 与 `BEAM` 上的对比结果。
- 它同时带有产品发布和招聘色彩，因此更适合当作工程思路与设计取舍样本，不适合直接当作跨系统通用结论。

## 主要观点

1. 生产环境里的记忆系统不应以“上下文越大越好”为默认目标，而应同时平衡准确率、token 成本和延迟。
2. 记忆系统不能只优化检索；抽取、检索和跨记忆推理如果彼此割裂，效果会在真实使用中很快触顶。
3. 新算法把写入路径改成单次 LLM 调用的 `ADD-only` 抽取，避免 `UPDATE / DELETE` 在对齐旧状态时抹掉时间演化信息。
4. Agent 自己生成的事实也应进入长期记忆，而不应只记用户明说的内容。
5. 检索层不应只依赖语义相似度，还要并行使用关键词和实体匹配，再做融合排序。
6. 现阶段最难的问题仍是长跨度时间推理、事件排序和多 session 推理；事实级与实体级匹配还不够。

## 关键内容

### 生产导向的记忆目标

- 资料明确把记忆评估拆成三件事：`accuracy`、`cost` 和 `performance`。
- 文中认为不少 benchmark 可以靠更激进的检索、超大上下文或更强模型抬分，但这不等于记忆系统本身更好。
- 作者尤其强调 `BEAM` 更贴近生产尺度，因为它覆盖 `1M` 和 `10M` token 级别的长上下文。

### 写入路径：单次、只追加、保留演化

- 旧算法先抽取候选事实，再和已有记忆做 `ADD / UPDATE / DELETE` 对齐。
- 新算法把流程折成一次 LLM 调用，并且只做新增；旧事实不被覆盖，新事实与旧事实并存。
- 这种做法的核心收益不是“存更多”，而是保留状态变化轨迹，让系统有机会回答“何时发生变化”“如何演化到现在”这类问题。
- 文中声称这一调整让抽取延迟大约减半；这里要保留证据边界，这个收益来自 Mem0 自家实现和评测环境，并非独立复现结果。

### 检索路径：实体层、多信号融合与词形归一

- 每条记忆都会再抽取实体，包括专有名词、引号中的文本和复合名词短语，并进入独立实体索引层。
- 查询时会并行跑三类评分：语义相似度、关键词匹配、实体匹配，再进行融合排序。
- 资料还特别提到词形归一这一类小改动，例如把 `attend` 和 `attending` 视作同一关键词族，以修复关键词检索漏召回问题。

### 记忆覆盖范围：用户事实之外，也包括 Agent 行为

- 新算法把 agent-generated facts 视为一等输入，例如“已经帮你订了 3 月 3 日的航班”这类执行结果。
- 这等于把记忆系统从“用户画像库”推进到“交互状态层”，让记忆更直接参与任务连续性。
- 文中还把抽取和检索描述为异步流程，试图把上下文治理负担从 Agent 主循环外移。

### 结果与证据边界

- 资料声称新算法在三个 benchmark 上都把单次检索调用的平均上下文压到 `7,000` token 以下，而许多全上下文方法通常需要 `25,000+`。
- 文中把 `LoCoMo` 的提升重点归因于时间问题和多跳问题，把 `LongMemEval` 的提升重点归因于 assistant memory 与 knowledge update，把 `BEAM` 的短板集中在大规模时间与事件结构建模。
- 但这些数字来自 Mem0 托管平台，作者也明确说其中包含开源 SDK 没有的专有优化，因此不应直接等同于“开源版本同样达到这些分数”。
- 原始摘录里 `LoCoMo` 的 mean tokens 被写成 `6,95`，看起来像截断或排版错误；在未回看图表原图前，精确数值应视为不确定。

## 纵向线索

- 这份资料把知识库里原本较抽象的“Agent 记忆层”推进到了更具体的工程层：真正难的不是有没有 memory，而是如何在有限 token 预算下写入、检索并保留演化。
- 它也和已有 Agent 工程综述形成呼应：记忆不该混成一个桶，而应分层、可回退、可按不同信号检索。
- 相比把上下文窗口继续拉长，这份资料更强调在窗口之外建立稳定的外部记忆表示。

## 与知识库的相关性

这条来源值得沉淀，不是因为它证明了某家产品“最好”，而是因为它给出了一个更细的工作定义：Agent 记忆系统至少要回答四个问题。

- 什么值得写入。
- 写入时是否保留状态演化。
- 检索时依赖哪些信号。
- 在固定 token 预算下，怎样把历史转成当前可用上下文。

## 可靠性判断

- 这是一份高相关度的一手产品说明，对理解 Mem0 自己如何定义问题、如何描述算法结构和评测目标有直接价值。
- 但它不是论文，也不是独立第三方评测；不少数字来自自家托管平台和自家 benchmark 解释框架。
- 因此，这页更适合沉淀设计思路、问题框架和证据边界，而不适合把具体分数直接固化为行业排序结论。

## 开放问题

- `ADD-only` 写入虽然保留演化，但长期如何做压缩、冲突处理和过期治理，文中没有展开。
