这是一篇围绕 `all-agentic-architectures` 项目和 agno 重写示例展开的 Agent 架构综述。它对知识库的长期价值不在于列全 17 个名字，而在于把 Agent 架构演进压成一个控制流问题：每次升级都在新增状态字段、路由逻辑、验证器、终止条件或副作用闸门。

## 这份资料是什么

- 资料来自公众号文章，作者基于 `all-agentic-architectures` 项目，用 agno 重新拆解多种 Agent 架构模式。
- 文章覆盖 Reflection、Tool Use、ReAct、Planning、PEV、Multi-Agent、Blackboard、Meta-Controller、Ensemble、Memory、Tree-of-Thoughts、Mental Loop、Dry-Run、Metacognitive、Self-Improvement、Cellular Automata 等模式。
- 它带有强解释和教学色彩，不适合直接当作框架标准；但它提供了一个很清楚的架构评估方法：看新增了什么 state、router 和 evaluator。

## 主要观点

1. Agent architecture 的本质不是 prompt engineering，也不是某个框架 DSL，而是控制流设计。
2. 真实 Agent 系统能否落地，关键在于状态是否被建模、控制流是否显式、错误是否能局部截断、副作用是否被闸门控制、系统是否知道何时停止。
3. Reflection 是最小质量闭环；Tool Use 打开外部世界；ReAct 把观察接回行动；Planning 把控制流本身变成可审计对象；PEV 把验证接入主回路。
4. 多 Agent 不只是多个模型并列，而是把认知分工、共享状态、入口路由或冗余投票写进图结构。
5. Memory、Graph Memory、Tree-of-Thoughts、Mental Loop 等模式分别解决长期状态、关系推理、回溯搜索和行动前模拟。
6. Dry-Run、Metacognitive 和 Self-Improvement 提醒：可靠 Agent 不只是更会做事，而是更知道什么时候预演、拒绝、升级人类或继续改进。
7. Evaluator 不是附属模块；闭环系统没有 evaluator，就不知道何时停、何时改、何时拒绝。

## 关键内容

### 六个固定问题

文章提出一个适合后续复用的分析框架：

1. 它要解决什么问题。
2. 它的 state 是什么。
3. 它的拓扑是什么。
4. 它的 router 怎么工作。
5. 它的失败模式是什么。
6. 什么时候该升级到下一种架构。

这套问题比“哪个 Agent 架构更先进”更有用，因为它强迫读者把系统能力落到可检查结构上。

### 控制能力的递进

- 从单次生成到 Reflection：新增 critic / refiner，把生成质量控制拆成多步。
- 从 Tool Use 到 ReAct：外部工具结果不只是事实补充，而是下一步行动的 observation。
- 从 Planning 到 PEV：计划不只是步骤清单，还要接入 verifier，失败时能重规划。
- 从 Multi-Agent 到 Blackboard / Meta-Controller / Ensemble：多 Agent 分别可以用于角色分工、共享状态调度、入口分诊和并行冗余。
- 从 Episodic / Semantic Memory 到 Graph Memory：长期状态既可以按事件/事实召回，也可以按关系和世界模型推理。
- 从 Tree-of-Thoughts 到 Mental Loop：推理可以变成搜索，行动可以先在模拟器里预演。
- 从 Dry-Run 到 Metacognitive：安全边界不只靠提示词，而要把副作用审批和自我能力边界写成控制流。

### Evaluator 是闭环系统的核心

文章把 evaluator 拆成五类：LLM-as-a-Judge、内置 critic、程序化验证、Human-in-the-Loop 和演示式验证。这里最值得保留的判断是：一旦系统开始反思、重规划、继续迭代、决定是否执行或升级人类，就已经进入闭环系统；闭环系统如果没有 evaluator，就只是会循环的 prompt。

## 纵向线索

- 这份资料把 [Harness Engineering](../concepts/harness-engineering.md) 里的控制面进一步具体化为 `state / router / evaluator / loop / parallel / memory / dry-run` 等可实现对象。
- 它也补强 [Agentic Engineering](../concepts/agentic-engineering.md)：工程师真正要设计的不是“万能 Agent”，而是任务所需的最小控制能力组合。
- 对 [Agent 训练](../concepts/agent-training.md) 而言，它提供了一张运行时架构地图：如果训练侧要优化长轨迹任务，奖励和环境也必须覆盖状态建模、验证、路由、工具和终止条件。

## 横向线索

- 与 [Agent 记忆系统](../concepts/agent-memory-systems.md)：文章中的 Episodic / Semantic / Graph Memory 提醒，记忆架构不是单一路线，而要看任务需要事件回忆、稳定事实还是关系推理。
- 与 [Agent 评测](../concepts/agent-evaluation.md)：文章对 evaluator 的强调与生产 evaluation harness 一致，只是更偏架构内的停机、重试、拒绝和升级机制。
- 与 [Spec-driven Development](../concepts/spec-driven-development.md)：Planning 和 PEV 把计划、验证与重规划显式化，说明 spec 进入执行链后还需要运行时 verifier。

## 与知识库的相关性

这条来源适合纳入现有结构，而不需要单独新建“17 种架构”概念页。它提供的是一套复盘语言：后续遇到任何新的 Agent 架构名词，都可以先问它新增了什么 state、router、evaluator，以及它把哪类失败从 prompt 里移到了控制流里。

## 可靠性判断

- 这是一篇工程解释文和项目走读，结构清楚，适合沉淀方法框架。
- 它并非论文或标准规范，部分架构分类来自作者对开源项目和 agno 实现的再组织。
- 因此本页保留控制流视角和失败模式判断，不把 17 种分类视为行业定版 taxonomy。
